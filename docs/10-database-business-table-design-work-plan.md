# 数据库业务表设计工作文档

## 1. 阶段目的

数据库业务表设计阶段用于把已确认的原型和业务流程落成稳定的数据结构。目标是让后续后台开发、小程序接口、订单状态流转都有清晰的数据来源。

这个阶段要避免临时建表和随手改字段。所有表、字段、状态、关联关系要先在文档中确认，再写 SQL。

## 2. 输入资料

- `docs/05-database-design.md`
- `docs/03-business-flows.md`
- `docs/09-prototype-design-work-plan.md`
- 已确认的小程序和管理后台原型说明

## 3. 输出物

- 业务表结构确认稿。
- 字段说明和枚举说明。
- 表关系说明。
- 初始化数据脚本。
- 可执行 SQL 文件。
- 数据库验证记录。

## 4. 设计范围

- 用户表。
- 服务分类表。
- 服务人员主表。
- 服务人员标签表。
- 服务人员证书表。
- 服务人员照片表。
- 服务人员工作经历表。
- 用户需求表。
- 需求推荐阿姨表。
- 预约面试表。
- 合同表。
- 服务订单表。
- 团购商品表。
- 拼团表。
- 团购订单表。
- 内容配置表。
- 系统消息表。
- 业务文件关联表，如 RuoYi 内置 `sys_oss` 不满足业务关联时再扩展。

## 5. 设计规则

- 先复用 RuoYi-Vue-Plus 已有用户、权限、文件表能力。
- 业务表只保存业务必要字段，不把页面展示临时字段硬塞进数据库。
- 状态字段统一用文档中定义的枚举。
- 图片、证书、合同文件优先保存 `ossId` 和 URL 关联信息。
- 所有时间字段要明确业务含义，如创建时间、审核时间、预约时间、成团时间。
- 第一版只考虑单管理员操作，不设计复杂权限表。
- 第一版支付为模拟支付，只保存模拟支付状态和支付时间。

## 6. SQL 文件规划

建议后续创建：

```text
sql/001_business_schema.sql
sql/002_seed_service_categories.sql
sql/003_seed_demo_content.sql
```

演示数据和正式基础数据分开，避免上线时混入测试数据。

## 7. 交付验收标准

- SQL 可以在本地 MySQL 执行成功。
- 核心业务表全部创建成功。
- 8 个服务分类初始化成功。
- 表字段能支撑已确认原型。
- 外键或逻辑关联关系清晰。
- 状态枚举与业务流程文档一致。
- 不需要手工修改数据库才能启动后续开发。
